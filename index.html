Project Workflow & Methodology

How the app dataset was researched, audited, and corrected — including how conflicting MCP server records were flagged for human review.

1

Initial Research with Gemini

Used Gemini to research the given list of apps and build baseline profiles — description, access model, and API surface — for each one.

2

Manual Spot-Check

Manually checked 25–30 apps by hand. Every field was accurate except one — the MCP server URL was frequently wrong or missing, so verification was scoped specifically to that field.

3

Automated Verification Loop Tavily

Built a loop to fetch and verify the correct MCP server URL for every app.

  • Used Tavily for the web search step — it makes real, live web search calls, so results reflect the latest available info (Gemini's built-in web search isn't free so I used Tavily)
  • For each app, I verified native MCP server URL by confirming the app's own domain appears in that URL
  • If no native URL was found, fell back to the best available third-party MCP server URL
4

Human-in-the-Loop for Conflicts

For records where the automated result was ambiguous or conflicting, added a human_verification column noting exactly what to check, alongside the candidate mcp_server_url — so a reviewer can verify the record quickly without redoing the research.

Data Generation Pipeline
1 generate-research.ts

Runs research for every app and outputs the baseline record to research.json.

↓

2 src/verify_with_tavily_gemini.ts

Reads research.json, verifies every MCP server URL, and produces two output files:

dataset_audit_log.json

Logs every record that was falsy, showing the old and corrected value — for example, the corrected MCP server type: native, third-party, or no MCP.

dataset_verified.json

The final, verified dataset. Records flagged with a human_verification column were checked manually against the app's info before being marked complete.
