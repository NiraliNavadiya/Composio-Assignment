Project Workflow & Methodology

How the app dataset was researched, audited, and corrected — including how conflicting MCP server records were flagged for human review.

1

Initial Research with Gemini

Used Gemini to research the given list of apps and build baseline profiles — description, access model, and API surface — for each one.

2

Manual Spot-Check

Manually checked 25–30 apps by hand. Every field was accurate except one — the MCP server URL was frequently wrong or missing, so verification was scoped specifically to that field.

3

Automated Verification Loop Tavily

Built a verification loop to fetch the correct MCP server URL for every app. Tavily was used for the web search step, since Gemini's native web search isn't free.

  • Fetch MCP server details via Tavily and check the app's official domain first
  • If an official/native MCP server URL exists on that domain, use it
  • If not, fall back to the best available third-party MCP server URL
4

Human-in-the-Loop for Conflicts

For records where the automated result was ambiguous or conflicting, added a human_verification column noting exactly what to check, alongside the candidate mcp_server_url — so a reviewer can verify the record quickly without redoing the research.

Final Verified Data Schema Attributes
app_name category one_line_description access_model api_surface mcp_status buildability_verdict primary_blocker docs_url url mcp_server_url human_verification
Falsy states were purged using automated filters. See dataset_audit_log.json for audit adjustments and dataset_verified.json for the final production output.
